Product Proposal · 2026

让 AI 文档
真正进入业务流程

从“生成一堆 Markdown / HTML 文件”，升级为可分享、可审阅、可批准、可追溯、可正式交付的文档闭环。

目标：5～50 人 AI 重度团队路径：开源组合二开验证周期：4 周汇报时长：12～15 分钟
本次申请：批准 4 周 MVP 验证，不是全面立项扩张
开场只讲一句：AI 已经能写报告，但还没有进入企业真实的审阅和交付流程。今天不是申请做一个新编辑器，而是申请用四周验证一个新的控制层。

02 · DECISION
Why Now

AI 解决了“写”，却放大了“交付”的混乱

01

生成成本趋近于零

报告、方案、计划、数据页可以连续生成，文档数量和迭代轮次快速增加。

02

审阅仍靠人工搬运

Markdown、HTML、截图、微信消息、邮件意见互相割裂，Agent 无法准确理解修改对象。

03

最终仍要正式交付

客户和企业需要权限、版本、批准、审计，以及符合模板的 Word/PDF。

新的瓶颈不是内容生产，而是：谁看了、评论了哪一版、哪些意见被批准、AI 改了什么、最终交付了什么。
把“AI 生成文档”类比成代码生成：代码有 Git 和 Pull Request，但业务文档没有对应的版本审阅基础设施。
03 · WHY NOW
Problem

当前流程在审阅环节断掉

今天的真实流程

Agent 生成 → 导出 HTML → 发文件 → 微信截图反馈 → 人工找段落 → 再让 AI 改 → report-final-v4-final2.html

文件失控反馈失焦版本不清无法审计
→

我们要建立的流程

稳定链接 → 逐段评论 → 负责人筛选 → Agent 按批准意见修改 → 新旧 Diff → 批准 → 企业格式导出

同一身份精确定位人工授权正式交付
1源文件Markdown / HTML 保留给 Agent
2稳定发布同一链接、不可变版本
3人工审阅文本、章节、图片评论
4授权修改负责人筛选后交给 Agent
5正式交付批准、DOCX、PDF、审计
不要花时间讲格式转换细节，重点是“反馈必须回到正确版本和正确段落”，这是闭环的技术难点和产品价值。
04 · PROBLEM
Who & Where

先服务高频、多人审阅、正式交付的团队

不是所有写文档的人都有需求。只有反复生成、反复审阅、需要正式交付，才会形成付费。

首要用户

AI 文档生产者

咨询顾问、研究员、解决方案经理、产品/研发负责人。

  • 每周生成多份报告
  • 需要汇总客户/领导意见
  • 希望 Agent 准确修改
关键体验

外部审阅者

客户、领导、法务、品牌与项目审核人。

  • 不理解 Markdown/Git
  • 不愿安装或注册工具
  • 只想打开、评论、批准
付费决策

团队负责人 / IT

关注交付效率、数据安全和模板统一。

  • 需要权限和审计
  • 需要 Word/PDF
  • 愿为私有部署付费
咨询与行业研究广告/内容代理软件外包解决方案与投标周期经营报告
如果老大追问“市场多大”，回答：目前不做宏观 TAM 推演，先验证这四类团队的周频闭环和付费点，避免用虚假大市场掩盖需求不确定性。

正向信号

Reddit、X、V2EX、Linux.do、小红书反复出现相同问题：Markdown 不适合交付，HTML 好看但难改，反馈无法回到 Agent。

反向证据

纯阅读器门槛低、容易复制；已有产品快速增长；早期同类产品也出现“注册后无人首次发布”的 onboarding 问题。

证据边界：互动量证明关注与痛点，不等于采购预算。因此下一步必须用真实团队、真实外部审阅和付费意向验证。
主动讲出反证会提高可信度：我们没有拿点赞冒充收入，验证计划就是为了补上最关键的付费证据。

08 · MVP FEATURES
Competitive Position

单点能力都有竞品，机会在组合闭环

已有产品分别解决

  • Google Docs / Notion：人工协作编辑
  • GitHub / Vercel：代码和预览审阅
  • Filestage / MarkUp.io：文件可视化反馈
  • DocSend：安全分享和访问分析
  • Gamma：AI 生成与漂亮交付

我们的独特组合

  • 机器友好的 Markdown/HTML 源制品
  • 外部访客无需账号即可审阅
  • 评论精确回到源文件与版本
  • 负责人授权后 Agent 才能修改
  • 中文企业 DOCX/PDF 正式交付
壁垒不在渲染 Markdown，而在身份、版本、定位、授权、审批、企业模板和私有部署形成的工作流。
坦诚说明：竞争不弱，所以不能打通用功能战。我们选择“中文企业交付 + Agent 安全回写”作为差异化切口。

10 · BUILD STRATEGY
Execution

四周交付可被真实客户使用的 MVP

WEEK 0

技术尖峰

四个关键 Demo：定位、批注嵌入、DOCX/PDF、许可证。

WEEK 1

稳定发布

Artifact、版本、CLI/MCP、Markdown/HTML 安全渲染。

WEEK 2

外部审阅

Review Link、评论、版本绑定、批准/要求修改。

WEEK 3

Agent 回写

Review Board、Brief、授权、Diff、审计。

WEEK 4

企业交付

Word/PDF、访问权限、10 个真实团队陪跑。

建议最小投入

1 名产品 Owner1 名全栈1 名前端/全栈设计与测试共享支持

若只有 1 名工程师，周期调整为 6～8 周，但仍按相同验证门槛执行。

真正稀缺资源

不是服务器，而是 10 个愿意把真实客户报告放进来审阅的试点团队。

强调试点客户和开发同等重要。没有真实外部审阅，再漂亮的 Demo 都不能证明产品成立。
11 · EXECUTION PLAN
Validation

用行为和付费决定继续，不用“感觉不错”

≥3 个团队连续四周每周发布 ≥3 份
≥30%外部打开文档产生评论/结论
≥50%READY Brief 最终产生新版本
≥2 个团队签署付费意向或支付试点费用
01
使用频率不足
只招募已有周频多轮审阅的团队。
02
仍复制到飞书/Word
重点观察审阅是否真正留在闭环内。
03
评论提示注入
原始反馈不可信，人工批准 Brief 后才执行。
04
DOCX 难度失控
首版只支持一个受限企业模板，复杂格式回退 PDF。
05
竞品快速跟进
聚焦中文企业交付、私有部署与 Agent 回写。
06
许可证污染
MIT 主骨架，AGPL/BSL 隔离，逐文件 NOTICE/SBOM。
停止条件：如果用户只使用“一键导出”而不使用审阅回写，则转向企业导出工具；如果四周后无人愿为模板、权限或私有部署付费，停止 SaaS 化。
这一页是管理层最关心的风险控制。重点是：项目有明确停止条件，四周后可以低成本止损或转向。
12 · VALIDATION & RISK
The Ask

希望批准三件事

1 · 四周验证冲刺

授权小团队基于开源方案完成 P0 闭环，不建设完整 SaaS，不扩展非核心功能。

2 · 真实试点入口

协调咨询、研究、外包或方案团队，提供 10 个正在发生的真实文档审阅案例。

3 · 明确继续/停止门槛

以周频闭环、外部审阅、Brief 应用和付费意向做决策。

四周后交付

  • 可发布 Markdown/HTML 的产品 Demo
  • 外部访客可评论、要求修改或批准
  • Agent 可按授权 Brief 发布新版本
  • 一个企业 DOCX 模板和 PDF
  • 10 个团队的行为数据与访谈
  • Go / Pivot / Stop 建议
建议决策：批准验证
用最小投入判断是否值得正式立项。
4 周 · 小团队 · 真实客户 · 明确止损
最后停在一个明确问题上：“是否同意用四周和最小团队，换取真实用户与付费证据？”不要以“大家有什么意见”结束。
