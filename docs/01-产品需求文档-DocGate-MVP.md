# DocGate 产品需求文档｜MVP v0.1

> 状态：可进入第一阶段开发  
> 更新日期：2026-08-20  
> 替代范围：替代旧版 PRD 中第一版产品的定义；旧版文档作为历史调研保留。

## 1. 产品定义

DocGate 是一个面向 AI 重度使用者的本地 Markdown 变更验收中间件。

用户在 Agent 生成的长 Markdown 文档上提出批注意见后，DocGate 将意见变成有稳定 ID 和定位证据的修改任务。Agent 修改文件并提交执行回执后，DocGate 以真实文件 Diff 为依据，为每条任务展示修改前、修改后、Agent 声明和确定性检查结果。用户可逐条接受或退回；退回时只生成未通过任务的返工包。

一句话价值：

> 批注工具告诉 Agent“哪里有问题”，DocGate 证明 Agent“是否真的按每条意见改对了”。

## 2. 目标用户与核心场景

### 2.1 核心用户

独立工作的 AI 重度使用者，例如产品经理、研究者、开发者、咨询顾问和内容创作者。他们具备以下特征：

- 经常让 Agent 生成或大幅修改 3,000 字以上的 Markdown 文档；
- 一轮会提出 5 条以上局部修改意见；
- 会连续进行两轮以上“批注—修改—复核”；
- 对遗漏、误改、顺手重写和虚假完成声明敏感；
- 当前主要靠聊天记录、肉眼全文重读或 Git Diff 检查结果。

### 2.2 典型任务

1. Agent 生成一份 PRD、技术方案或研究报告 Markdown。
2. 用户通过批注器对具体段落提出意见。
3. DocGate 将批注规范化为修改任务，并生成 Agent 可读的 Markdown 返工包。
4. Agent 修改原文件，同时提交结构化执行回执。
5. DocGate 比较基线和结果，将真实 Diff 归因到任务。
6. 用户逐条接受、要求返工或要求澄清。
7. DocGate 只把未通过任务发送到下一轮，已接受内容成为新的受保护基线。

## 3. 要解决的问题

现有批注产品已经较好地解决“选中一段文字并把意见交给 Agent”，但意见发出后仍存在验收断层：

- Agent 说“已完成”，不代表文件真的变化；
- 文件发生变化，不代表改的是正确位置；
- 改了正确位置，不代表完整满足意见；
- Agent 可能顺手改动未授权内容；
- 多条意见与多个 Diff hunk 往往是多对多关系；
- 用户最终仍需要从头通读全文，批注节省的时间被验收吃掉。

DocGate 的产品边界是补齐这个断层，而不是再造一个 Markdown 批注器。

## 4. 设计原则

### 4.1 三种信息、三种信任等级

| 信息 | 含义 | 信任方式 |
| --- | --- | --- |
| 人的批注 | 被授权的修改请求 | 作为任务来源，保留原文 |
| Agent 回执 | Agent 声称做了什么 | 不可信声明，只作为解释线索 |
| 真实 Diff | 文件实际发生了什么 | 客观证据，是验收基础 |

系统不得仅凭 Agent 回执把任务标记为通过，也不得用可选的模型判断替代人的最终接受。

### 4.2 双层状态，不制造“伪确定性”

系统分别记录 Agent 执行状态、机器验证状态和人工决策。`agent=addressed` 不等于 `verification=pass`，二者都不等于 `human=accepted`。

### 4.3 逐任务验收，而非全文重读

每个任务卡必须把完成判断所需信息聚合在一起：原意见、锚点上下文、修改前后、相关 Diff、Agent 回执、检查结果和决策按钮。

### 4.4 未归因修改必须显式暴露

任何无法归因到任务的 Diff 都进入“未声明修改”收件箱。不得隐藏、自动合并或默认接受。

## 5. MVP 用户闭环

```text
Agent 生成 Markdown
→ DocGate 建立不可变基线
→ Plannotator 完成批注
→ DocGate 生成 Change Tasks + agent-brief.md
→ Agent 修改原文件并提交 receipt.json
→ DocGate 计算真实 Diff、归因与确定性检查
→ 用户在验收页逐任务接受 / 返工 / 澄清
→ DocGate 生成只包含未通过任务的 rework-brief.md
→ 下一轮修改或会话接受
```

## 6. 功能需求

### P0-01 建立审阅会话

- 用户选择工作区内一个 `.md` 文件开始会话。
- 系统保存不可变基线、SHA-256、受控源路径、创建时间和 schema 版本。
- 会话数据写入 `.docgate/sessions/{session_id}/`，重启后可恢复。
- 同一文件同一时刻只允许一个活跃写会话；冲突时给出可理解错误。

验收：修改源文件后，基线仍保持原样；重启服务仍能列出会话。

### P0-02 接收并规范化批注

- 默认通过 Plannotator 适配器接收 JSON；适配器与领域模型隔离。
- 每条批注生成不可变 `task_id`。
- 保留原批注文本以及 exact quote、prefix、suffix、occurrence、行范围、heading path 等可获得的定位证据。
- 无法唯一定位时保留任务，但标记 `locator_status=ambiguous`，不得静默猜测。

验收：至少 5 条批注可生成 5 个稳定任务，重新加载后 ID 不变。

### P0-03 生成 Agent 返工包

- 输出人类和 Agent 都可读的 `agent-brief.md`。
- 输出机器可读的 `tasks.json` 与 `receipt.schema.json`。
- 每条任务包含目标、授权范围、禁止改动范围、定位上下文和回执要求。
- 不绑定某一家 Agent；用户可将文件交给 Codex、Claude Code 或其他能读写工作区的 Agent。

验收：不了解 DocGate 内部实现的 Agent 能按返工包完成文件修改并产出合法回执。

### P0-04 接收 Agent 执行回执

- 回执必须包含会话 ID、基线 hash、结果 hash、每条任务的 outcome、摘要和声称的修改范围。
- 后端用 Pydantic 严格校验；未知字段可按版本策略处理，必填字段缺失必须拒绝。
- 回执只记录声明，不直接修改任务的人工状态。

验收：合法回执被持久化；错误会话、过期基线、伪造结果 hash 和非法枚举被明确拒绝。

### P0-05 真实 Diff 与任务归因

- 以磁盘上的基线和结果快照计算真实行级 Diff。
- 建立 `task ↔ hunk` 多对多关系，不强制一条任务只对应一个 hunk。
- P0 归因至少结合：目标锚点是否被触达、变更行与锚点距离、Agent 声称范围。
- 归因结果包含方法、证据和置信等级；低置信不得伪装成确定匹配。
- 没有关联任务的 hunk 进入未声明修改列表。

验收：能识别“声称完成但没有修改”“改了相同文本的错误段落”“一条任务改多处”“多条任务共享一个 hunk”和“顺手修改无关段落”。

### P0-06 确定性验证

P0 必须实现：

- 基线 hash 与结果 hash 一致性；
- 文件是否实际发生变化；
- 任务锚点附近是否被触达；
- 声称的修改范围是否存在真实 Diff；
- Markdown 文件能否按选定解析器解析；
- front matter（如存在）是否仍可解析；
- 未声明修改检测；
- 源文件被会话外修改时的 stale baseline 检测。

P0 不自动判断开放式文字意见是否“语义上完全正确”。语义完成度由人验收；独立模型验证属于 P1 可选项。

### P0-07 逐任务验收界面

- 首页可列出会话及其状态。
- 会话页显示进度和未声明修改数量。
- 任务卡显示原意见、before/after、相关 Diff、回执、检查结果和不确定性。
- 人工决策为 `accepted`、`rework_requested`、`clarification_requested`，并可填写原因。
- 未声明修改独立展示，用户必须接受或要求撤销，才能接受整个会话。
- 刷新或服务重启后，人工决策不丢失。

### P0-08 生成返工包和接受会话

- 返工包只包含 `rework_requested`、`clarification_requested` 及尚未处理的未声明修改。
- 已接受任务列为受保护内容，明确要求 Agent 不得重做或回退。
- 只有所有任务和未声明修改均已有明确人工决策时，才允许接受会话。
- 接受后结果文件成为下一轮基线，但历史基线、证据和决策不可变。

## 7. 非功能需求

- 本地优先：P0 数据不上传 DocGate 自有云端。
- 隐私：日志不得记录完整文档、API Key 或批注全文；错误响应不得暴露堆栈。
- 恢复：进程退出后会话、回执、证据和人工决策可恢复。
- 写入安全：JSON 原子写入，单会话文件锁；不得覆盖历史基线。
- 文件安全：只接受工作区内普通 UTF-8 `.md` 文件；拒绝路径遍历、工作区外路径和危险符号链接。
- 范围基线：P0 目标文件大小不超过 2 MiB；更大文件明确提示未验证，而非静默失败。
- 可解释：所有机器结论必须带规则 ID 和证据，不只显示一个分数。
- 可移植：领域协议不绑定 Plannotator 或具体 Agent。

## 8. 明确不做

- 自研或 fork Markdown 批注 UI；
- 多人同时审阅、评论线程、团队空间、账号、权限和通知；
- 云端分享链接和托管；
- Word、PDF、任意 HTML 的导入导出；
- WYSIWYG 通用文档编辑器；
- 自动调用 Agent、托管 Agent 密钥或无限自主执行；
- 由模型自动做最终接受决定；
- SaaS 计费、审计后台、企业合规能力。

## 9. 成功指标与停止条件

### 9.1 MVP 通过门槛

在 3 份真实的 3,000 字以上 Markdown 文档、每份至少 5 条意见上：

- 100% 批注形成稳定任务并可回溯原上下文；
- 100% 真实 Diff 被归因到至少一条任务或进入未声明修改列表；
- 所有“回执声称完成但文件无对应变化”的注入案例被发现；
- stale baseline 和错误结果 hash 被发现；
- 用户可不阅读全文，仅通过任务卡完成一轮验收；
- 服务重启后会话与决策完整恢复；
- 自动化测试和人工端到端验收全部通过。

“语义是否改对”不设机器 100% 命中目标，P0 由人做最终判断。

### 9.2 产品验证指标

- 与“重新通读全文 + 手工对照 Diff”相比，单轮验收用时下降至少 30%；
- 至少 3 名目标用户愿意在一周内重复使用两次；
- 至少一半测试用户认为“未声明修改”和“逐任务返工包”有独立于 Plannotator 的价值。

### 9.3 停止或转向

若连续测试表明用户仍必须全文重读、逐任务证据无法降低验收成本，或用户只需要普通 Diff，则停止扩展 UI 和模型验证，转向更轻量的 CLI/协议工具。

## 10. 后续路线（非本阶段承诺）

- P1：Markdown AST 级结构 Diff、链接/资源/Mermaid 检查、锚点迁移。
- P1：可选的独立语义验证器，输出 `pass/warn/fail/uncertain`，永不自动接受。
- P2：更多批注器适配、更多 Agent 回执适配、CLI 安装与桌面封装。
- 只有出现明确需求后：团队协作、云端和更多文档格式。

## 11. 暂定项

- 产品正式名称暂用 DocGate，不阻塞开发。
- P0 默认 macOS 优先、Linux 兼容；Windows 在分发阶段验证。
- Plannotator 的具体版本和 CLI 参数在开工环境自检时锁定，并在依赖说明中记录；发布二进制前重新核对许可证及通知义务。
- P0 不需要模型 API Key，因为产品不代替 Agent 执行，也不启用语义验证器。
