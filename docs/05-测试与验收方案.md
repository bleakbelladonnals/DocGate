# DocGate 第 1 阶段测试与验收方案

> 原则：验证“证据链是否可靠”，而不只验证页面能否打开。任何测试失败都不得通过删除用例、放宽断言或改写验收标准来掩盖。

## 1. 测试分层

| 层 | 工具 | 目标 | 每次交付是否必跑 |
| --- | --- | --- | --- |
| 领域单元测试 | pytest | schema、状态机、定位、Diff、归因、规则、返工范围 | 是 |
| 持久化与安全测试 | pytest | 原子写、重启恢复、损坏处理、路径安全、锁 | 是 |
| API 集成测试 | pytest + httpx | 结构、错误、幂等、状态转换 | 是 |
| 前端静态检查 | TypeScript + ESLint | 类型与代码错误 | 是 |
| Web 关键流程 | Playwright | 逐任务决策、刷新恢复、返工/接受门槛 | 是 |
| 外部工具冒烟 | 实际 Plannotator CLI | 已锁定版本的批注 JSON 适配 | 阶段验收前；不可用时明确待验 |
| 真实文档人工验收 | 浏览器 + 外部 Agent | 产品价值与可读性 | 阶段验收前 |

本阶段没有模型调用，因此不运行“真实模型冒烟”。如果实现过程中擅自引入模型，则必须先更新技术适配声明、配置与测试方案，不能把它藏在实现中。

## 2. 固定测试资产

在 `fixtures/` 生成不含私人内容的文件：

- `simple.md`：不同标题下 5 个唯一段落；
- `duplicate-paragraphs.md`：两个相同段落，occurrence 不同；
- `frontmatter.md`：含 YAML front matter；
- `reorder.md`：章节移动与局部编辑；
- `large.md`：接近 2 MiB 的边界样例，由测试确定性生成，不提交巨大重复文件；
- `invalid-utf8.md`：测试运行时生成；
- `annotations/*.json`：合法、缺字段、重复 ID、ambiguous locator 等；
- `receipts/*.json`：合法、伪造 hash、漏任务、越界 claimed range 等。

fixture 必须可公开、可重复生成，不能复制用户私人文档全文。

## 3. 领域单元测试

### 3.1 Schema 与回执

- 合法 tasks/receipt/evidence/decision 可序列化再读取；
- 必填字段缺失、错误枚举、错误 ID、非法时间、错误 hash 长度被拒绝；
- 回执漏任务、重复任务、夹带其他 Session/Round task 被拒绝；
- `partial/clarification/blocked/not_applicable` 缺少 notes 被拒绝；
- receipt base/result hash 与真实快照不符产生对应 fail；
- schema v1 未知兼容字段的策略明确并有测试，不静默吞掉关键字段。

### 3.2 状态机

- 每一条合法转换通过；
- 非法跳转全部拒绝；
- 重复 decision 幂等；
- `accepted` 后任何写入拒绝；
- `verifying` 中断后可从结果快照重跑；
- 返工创建新 Round，旧 Round 文件 hash 不变。

### 3.3 Locator 与归因

- unique quote + 行区间重叠得到 certain；
- 相同文本通过 occurrence 定位到正确段落；
- occurrence 缺失且文本重复得到 ambiguous，不得 certain；
- 同一 task 对应多个 hunk；
- 同一 hunk 对应多个 task；
- 纯插入紧邻锚点得到 likely；
- 只有 Agent claimed range 支持时为 weak，并仍进入未声明修改；
- heading 内远离锚点的变化不会错误高置信归因；
- 无任何关联的 hunk 必须出现在未声明修改列表。

### 3.4 确定性规则

- 零 Diff + addressed → `DG-DIFF-001 fail`；
- claimed range 无真实 hunk → `DG-CLAIM-001 fail`；
- addressed 无 certain/likely hunk → `DG-TASK-002 fail/uncertain`；
- front matter 被破坏 → `DG-FM-001 fail`；
- 源文件在结果快照后又变化 → `DG-BASE-001 fail`；
- 无关变化 → `DG-SCOPE-001 warning` 且需要人工决策；
- 不把语义不同意自动判断为机器 fail，避免越过 P0 能力边界。

## 4. 持久化与文件安全测试

- 每种可写状态落盘后重建服务，读取结果一致；
- 模拟临时文件写入失败，正式文件保持上一版本；
- 模拟进程在 rename 前退出，恢复逻辑不读取半文件；
- JSON 损坏返回 `DATA_CORRUPTED`，不覆盖损坏证据；
- 两个写请求竞争同一 Session 时，一个成功，另一个得到可重试冲突；
- 拒绝 `../`、绝对外部路径、工作区外符号链接、目录、非 `.md`、非 UTF-8 和超过上限的文件；
- 输出协议只存工作区相对路径；错误和日志不含文档正文；
- 基线、历史 Round 和已接受 Session 不可覆盖。

## 5. API 集成测试

至少覆盖一条完整成功链路和以下错误：

- 统一错误结构始终是 `error.code + error.message`；
- 不存在 Session/Task/Hunk 返回稳定错误码；
- 请求体多余/缺失/错误字段得到明确 4xx；
- 当前状态不允许的动作返回 `INVALID_STATE_TRANSITION`；
- 未处理所有任务或 hunk 时 `accept` 被拒绝，并返回未完成项摘要；
- verify 重复调用结果确定且不会创建不同 hunk ID；
- decision 重复提交幂等；
- API 不返回绝对工作区路径、堆栈或内部临时文件名；
- 非 loopback Host/非法 Origin 的状态修改被拒绝；
- 本地会话 token/CSRF 防护有效且不出现在 URL 和日志中。

## 6. 前端与 E2E

### 静态门槛

- `npm run typecheck` 通过；
- `npm run lint` 通过；
- 生产构建通过；
- 不在前端实现状态转换、hash、Diff 归因或接受门槛。

### Playwright 关键流程

1. 打开有 5 个任务的会话。
2. 筛选 `warning/fail/uncertain`。
3. 每张任务卡能展开 before/after、hunk、回执和检查证据。
4. 分别选择 accepted、rework、clarification 并输入原因。
5. 刷新后决定仍在；重启 API 后仍在。
6. 未声明修改存在时无法接受会话。
7. 对未声明修改做 accepted/revert_requested 决策。
8. 生成返工包，内容只包含失败项并列出 protected 项。
9. 所有项接受后会话进入 accepted，写操作禁用。
10. 加载失败、数据损坏、stale baseline 均有可执行的恢复提示。

可访问性最低要求：按钮可键盘操作，有可见焦点，状态不只依赖颜色，表单有 label，Diff 删除/新增有文本或符号说明。

## 7. P0 失败注入矩阵

| ID | 注入方式 | 必须观察到的结果 |
| --- | --- | --- |
| FI-01 | 回执 addressed，但源文件未变 | Diff 为空；`DG-DIFF-001` 与相关 task 检查失败；不能自动接受 |
| FI-02 | 5 个任务只修改 4 个 | 漏改 task 无 certain/likely hunk；任务卡明确暴露 |
| FI-03 | 两个相同段落，改错 occurrence | 目标 task 不得 certain；错误位置 hunk 进入未声明/低置信区域 |
| FI-04 | 只完成意见的一半并声称 addressed | 机器证明“触达”，但不能声称语义完整；任务卡交人判为返工 |
| FI-05 | receipt result hash 伪造 | `DG-HASH-002 fail`，拒绝进入正常人工验收 |
| FI-06 | 正确修改外顺手重写其他章节 | 无关 hunk 全部进入未声明修改 |
| FI-07 | 删除目标小节 | Diff 正确显示删除；机器不自动视为满足意见；交人验收 |
| FI-08 | Agent 修改前源文件已偏离本轮 base | stale baseline 明确失败，不在错误基线上继续归因 |
| FI-09 | 一条意见同时改标题和正文 | 一个 task 可关联多个 hunk |
| FI-10 | 两条意见通过同一段改动一起满足 | 一个 hunk 可关联多个 task，分别人工决定 |
| FI-11 | 移动章节并局部修改 | 低置信/未归因明确展示，不伪装为精确语义 Diff |
| FI-12 | Agent 使用 clarification 而不修改 | 合法回执；任务进入需澄清，不把无修改当系统异常 |
| FI-13 | verify 后继续手改源文件 | 接受前 `DG-BASE-001 fail`，要求重新提交/验证 |
| FI-14 | 返工时回退上一轮已接受内容 | protected 区变化进入未声明修改并阻止无感接受 |
| FI-15 | 服务在保存 decision 时中断 | 恢复后只能是旧完整值或新完整值，不出现半 JSON |

## 8. 外部 Plannotator 集成冒烟

开工时先锁定实际可用版本并保存一个最小契约 fixture。冒烟步骤：

1. 对 `fixtures/simple.md` 启动 Plannotator；
2. 创建 5 条包含文本选择的批注；
3. 通过经验证的 JSON 输出路径结束审阅；
4. DocGate 适配器导入，生成 5 个 task；
5. 检查 exact quote、prefix/suffix、行号、heading path 和 external ID；
6. 记录工具版本和命令，不记录用户文档内容。

如果版本不兼容或无法自动捕获输出：

- 通用 `import-annotations` 流程仍须通过；
- 报告“Plannotator 集成待验”，不得将 fixture 测试描述为真实外部冒烟；
- 不得为赶进度复制或 fork 整个批注 UI。
- 在真实外部冒烟通过前，第 1 阶段只能报告“核心链路已就绪、外部集成阻塞”，不能标记完成。

## 9. 三份真实文档人工验收

建议从当前仓库的长文档中选择三份副本作为私有人工样例，不把产生的 `.docgate` 运行数据提交到 Git：

- `AI文档处理中间件PRD.md`；
- `AI产品Vibe Coding通用技术栈手册.md`；
- 一份新生成或用户指定的 3,000 字以上 Markdown。

每份至少创建 5 条意见，包含：局部改写、补充指标、删除内容、跨两处修改、需要澄清各一种。由外部 Agent 修改并提交回执。

记录：

```markdown
## 验收记录
- 日期：
- 文档/字数：
- Agent：
- 任务数 / hunk 数 / 未声明 hunk 数：
- 从打开验收页到完成决定的时间：
- 是否需要全文重读：是/否；原因：
- 发现的遗漏/误改数量：
- 与手工全文复核相比的主观时间变化：
- 阻塞问题：
- 结论：通过 / 返工 / 不通过
```

## 10. 发布判定

第 1 阶段只能在以下条件全部满足时标记完成：

- 后端、持久化、API、前端检查和 Playwright 全通过；
- FI-01 至 FI-15 全部得到预期结果；
- Plannotator 真实冒烟通过；若外部环境阻塞，只能将其列为阻塞项，不能把阶段标记完成；
- 三份真实文档完成一轮人工验收；
- README 写清实际环境、启动、操作、限制、测试命令和未通过项；
- 临时服务和端口已清理，除非用户明确要求保留预览；
- 没有用 mock/fixture 冒充外部工具或真实用户验收。
