# Codex Goal 模式开发提示词

## 使用方法

在 Codex 中打开本项目根目录，复制下面整段内容发送。它的目标是把第 1 阶段做到“可交给产品经理验收”，不是提前完成路线图中的所有阶段。

```text
/goal 在当前仓库完成 DocGate 第 1 阶段 MVP，使其达到“自动化验收全部通过、真实 Plannotator 集成已验证、可交给产品经理按清单做三份真实文档人工验收”的状态；持续推进开发、运行、测试和修复，只有达到下述可验证停止条件或遇到确实需要我提供权限/安装环境/人工操作的阻塞时才停下来。

开始前必须完整阅读并按优先级执行：
1. AI产品Vibe Coding通用技术栈手册.md（安全、隐私、恢复与验收底线最高）；
2. docs/01-产品需求文档-DocGate-MVP.md（业务范围）；
3. docs/02-技术适配声明.md（技术裁决）；
4. docs/03-第一阶段技术开发文档.md（本阶段实现边界）；
5. docs/04-数据协议与状态机.md（字段、规则和状态契约）；
6. docs/05-测试与验收方案.md（用例和通过门槛）；
7. README.md 与当前目录全部已有代码/配置。

根目录旧版 AI文档处理中间件PRD.md 和三个 HTML 文件仅是历史调研，不是 MVP 开发依据；不要实现其中的团队、账号、分享、权限、导出或 SaaS 范围。不要自研、复制或 fork 批注 UI；通过独立适配器复用 Plannotator，并保留通用 JSON 导入回退路径。

执行要求：
- 先做只读自检：确认当前 Git 状态、未提交文件、Python 3.11、Node.js 22/npm、端口、Plannotator 的实际可用版本和 CLI/JSON 契约。当前目录若仍不是 Git 仓库，在确认根目录无误后初始化 Git，并用 .gitignore 排除 .env、.venv、node_modules、.next、.docgate、日志和缓存；不得修改或删除历史文档。
- 如果缺少 Python 3.11、Node.js 22 或必须的外部环境，先给我一条非技术人员可照做的精确操作指令；同时继续所有不受阻塞的工作。不要把 mock 或 fixture 冒充真实外部集成。
- 按 docs/02-技术适配声明.md 采用纵向切片：Python 3.11 + FastAPI + Pydantic + pytest 的核心/本地 API，Next.js + TypeScript + App Router + Tailwind 的正式最小验收页，npm 与锁文件。除非文档中的触发条件真的出现，否则不引入数据库、模型 SDK、SSE、任务队列、桌面壳或微服务。
- 业务规则只实现一次，放在后端 domain/services；CLI 与 /api/v1 调用同一实现；前端不得复制状态机、Diff 归因、hash 或接受门槛。
- 先完成一个最小纵向成功路径，再扩展错误路径：建立不可变 Round 基线 → 导入至少 5 条批注并生成稳定 task → 生成 agent-brief.md 和 receipt.schema.json → 接收 Agent 修改与 receipt → 结果快照、真实 Diff、多对多任务归因和确定性检查 → Web 逐任务决策与未声明修改决策 → rework/accept。
- 所有运行期数据按 docs/04 的 schema_version、Session/Round 结构持久化；每轮历史不可覆盖；JSON 原子写入并加单会话锁；损坏数据不得自动覆盖；源路径必须受工作区根目录限制。
- 锁定并记录实际验证过的 Plannotator 版本与命令。外部契约只能存在于 adapters 层；保留 fixture 契约测试和 import-annotations 回退入口。未经必要性验证不要全局安装工具；优先使用项目本地、可复现依赖。
- P0 不调用任何模型、不索取 API Key、不实现语义自动裁决。Agent receipt 是不可信声明；真实 Diff 是客观证据；human decision 才是最终接受。UI 必须把三者分开显示。
- API 全部使用 Pydantic 请求/响应模型和统一 error.code/error.message；错误不返回堆栈、绝对敏感路径或文档原文。服务只监听 loopback，并实现 Host/Origin 与状态修改请求防护。
- Prompt 不散落在代码中。本阶段没有模型 Prompt；agent-brief 与 rework-brief 使用独立、版本化的确定性模板，并包含正反例与 receipt 约束。
- 维护 docs/开发进度日志.md：每个检查点只记录已完成能力、实际运行命令和结果、仍存在的失败/风险、下一步；不要写虚假的通过结论。
- 保留用户已有文件和修改。使用小范围修改，不为匹配示例目录重构合理代码，不擅自扩大产品范围。

必须执行并修复到通过的验证：
1. 后端领域、状态机、持久化、安全路径和 API 的 pytest；
2. 前端 typecheck、ESLint、组件/关键逻辑测试和 production build；
3. Playwright 完整成功路径、刷新/重启恢复、返工门槛和接受门槛；
4. docs/05 中 FI-01 至 FI-15 失败注入，逐项保留可追踪测试；
5. 对锁定版本的真实 Plannotator 跑一次 simple.md 五条批注冒烟，记录版本、命令和结果；
6. 启动完整应用，用浏览器实际检查会话列表和验收页的加载、空、错误、证据、决策、返工和接受状态；
7. 检查日志、错误响应和 Git 状态，确认没有秘密、用户文档正文、运行数据、缓存或构建产物被提交。

停止条件：
- docs/03 规定的 CLI、/api/v1、持久化协议和两张核心页面均已实现；
- 所有适用自动化命令真实通过，FI-01 至 FI-15 全部得到预期结果；
- Plannotator 真实集成冒烟通过，不能通过时必须给出证据、已尝试路径和唯一剩余阻塞，不得声称完成；
- README 已更新为非技术人员可照做的安装、启动、完整演示、测试、数据位置、恢复与限制说明；
- docs/开发进度日志.md 记录最终命令和结果，并生成一份“产品经理下一步只需做什么”的三份真实文档人工验收清单；
- 临时服务和端口已清理，除非我明确要求保留预览。

达到停止条件后再汇报：先给可运行结果和启动方式，再列自动化/集成验证证据、尚待我亲自完成的人工验收，以及严格限于第 1 阶段的已知限制。不要只生成计划、脚手架或文档后就结束。
```

## Goal 完成后的人工动作

Goal 的“完成”代表工程已达到可验收状态，不代表产品价值已经由真实用户验证。你仍需要按 `docs/05-测试与验收方案.md` 第 9 节，对三份真实长文档亲自完成一轮审阅并记录时间与是否需要全文重读。
