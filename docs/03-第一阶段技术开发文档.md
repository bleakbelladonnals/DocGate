# 第 1 阶段技术开发文档｜单文件逐任务验收闭环

> 配套文档：`docs/01-产品需求文档-DocGate-MVP.md`、`docs/02-技术适配声明.md`、`AI产品Vibe Coding通用技术栈手册.md`。  
> 本文档只覆盖第 1 阶段。开发时不得提前实现第 2 阶段能力。

## 一、阶段目标

### 交付范围

在一个本地工作区内，对一个 UTF-8 Markdown 文件完成：建立基线、导入/采集批注、生成 Agent 返工包、接收 Agent 回执、计算真实 Diff、任务归因、逐任务人工验收、生成下一轮返工包和接受会话。

### 阶段产物

- 可从命令行启动的 DocGate 本地应用；
- 受控 loopback FastAPI；
- Next.js 验收页；
- Plannotator JSON 适配器及通用 JSON 导入回退路径；
- 带版本、可恢复的本地会话目录；
- 任务、回执、证据与决策 Pydantic 模型；
- 自动化测试、E2E 测试和人工验收样例；
- 完整 README、`.env.example`、启动/验证说明。

### 验收标准

- 以至少 5 条批注跑通完整一轮；
- 每个真实 Diff hunk 被关联到任务或进入未声明修改列表；
- 识别测试方案中的 P0 失败注入；
- 人工决策刷新和重启后不丢失；
- 只能在所有任务和未声明修改均有决定后接受会话；
- 所有适用自动化检查通过，并完成三份真实文档人工验收。

### 明确不做

- 自研批注界面、团队与账号、云端、更多格式；
- AST 级语义结构 Diff、独立模型验证、自动最终接受；
- 自动操作具体 Agent 或管理模型 Key；
- 桌面端封装、安装器、应用商店分发；
- 多文件原子变更集。

### 本阶段主链路

```text
review file.md
→ baseline + tasks + agent-brief
→ 外部 Agent 修改 file.md 并写 receipt.json
→ submit + verify
→ Web 任务卡人工决策
→ rework 或 accept
```

## 二、技术适配摘要

- 开发路径：纵向切片，因为逐任务验收界面决定核心价值是否成立。
- 采用默认方案：Python 3.11、FastAPI、Pydantic、pytest、Next.js、TypeScript、Tailwind、npm、Git。
- 启用按需模块：Plannotator 外部适配器、Markdown 解析、原子文件持久化、Playwright。
- 暂缓：关系型数据库、模型 SDK、SSE、任务队列、桌面壳。
- 核心逻辑必须位于后端领域/服务层；CLI 和 API 复用同一实现，前端不得复制判定规则。

## 三、技术栈与模型

### 后端

- Python 3.11.x；
- FastAPI + Uvicorn；
- Pydantic v2；
- Typer 用于本地 CLI；
- pytest + pytest-asyncio + httpx；
- Markdown 解析库和 front matter 库在开工技术尖峰后锁定一个版本；
- 标准库 `hashlib`、`difflib`、`pathlib` 完成 P0 hash、行级 Diff 和路径控制；只有标准库方案无法满足验收时才增加 Diff 库。

依赖使用 `pyproject.toml + 锁文件`，提交可复现版本。新增库必须在 README 说明用途。

### 前端

- Node.js 22 LTS；
- Next.js + TypeScript + App Router；
- Tailwind CSS；
- ESLint + TypeScript；
- Playwright 用于关键交互 E2E。

### 模型

本阶段不调用模型，不需要 Key，不存在可用 mock 冒充的“真实模型冒烟”。Agent 是外部执行者，只通过文件协议接入。

## 四、环境与配置

`.env.example` 只包含非秘密默认项：

```dotenv
DOCGATE_WORKSPACE_ROOT=/absolute/path/to/workspace
DOCGATE_HOST=127.0.0.1
DOCGATE_PORT=8765
DOCGATE_LOG_LEVEL=INFO
DOCGATE_MAX_MARKDOWN_BYTES=2097152
DOCGATE_PLANNOTATOR_COMMAND=plannotator
```

规则：

- 服务只监听 `127.0.0.1`，P0 不允许配置 `0.0.0.0`；
- 工作区根目录启动时解析成绝对路径，所有源文件必须是其普通子文件；
- `.docgate/`、`.env`、缓存、日志和测试临时文件加入 `.gitignore`；
- P0 没有秘密配置，但日志规则仍按未来含敏感文档处理；
- 默认端口冲突时选用空闲 loopback 端口，并明确打印实际地址。

## 六、数据、资产与状态

### 持久化选择

采用带 `schema_version` 的文件清单。原因：P0 单用户、单机、低并发，用户需要能直接备份和检查会话。每次写入采用同目录临时文件、flush/fsync、原子 rename；单会话写操作持有文件锁。

### 会话目录

```text
.docgate/
├── index.json
└── sessions/{session_id}/
    ├── session.json
    ├── tasks.json
    └── rounds/
        └── 0001/
            ├── round.json
            ├── baseline.md
            ├── annotations.raw.json
            ├── agent-brief.md
            ├── receipt.schema.json
            ├── receipt.json
            ├── result.md
            ├── diff.json
            ├── evidence.json
            ├── decisions.json
            └── rework-brief.md
```

- 每轮 `baseline.md` 创建后不可覆盖；返工创建新轮次，不覆盖旧证据；
- `result.md` 是提交时快照，不直接依赖之后继续变化的源文件；
- `index.json` 只是可重建索引，真实会话状态以各会话目录为准；
- 发现 JSON 损坏时不覆盖原文件，返回 `DATA_CORRUPTED` 并说明备份/恢复路径；
- schema 升级必须保留读取旧版本或提供显式迁移命令。

### 状态机

```text
BASELINED
→ FEEDBACK_READY
→ AGENT_WORKING
→ RESULT_SUBMITTED
→ VERIFYING
→ HUMAN_REVIEW
→ ACCEPTED
  或 REWORK → AGENT_WORKING
```

具体字段和合法转换见 `docs/04-数据协议与状态机.md`。后端拒绝非法跳转，前端只展示当前合法动作。

## 七、API / 工具设计

### CLI

```text
docgate doctor
docgate review <document.md>
docgate import-annotations <session_id> <annotations.json>
docgate brief <session_id>
docgate submit <session_id> --receipt <receipt.json>
docgate verify <session_id>
docgate inspect <session_id>
docgate rework <session_id>
docgate accept <session_id>
```

- `doctor` 检查 Python、Node/npm、Plannotator、端口和工作区权限，不读取或输出文档正文。
- `review` 创建基线并优先调用经过锁定版本验证的 Plannotator；若外部工具不可用，返回明确安装/版本提示，不自动从网络安装。
- `import-annotations` 是稳定回退入口，也是自动化测试入口。
- `inspect` 启动本地 API/前端并打开当前会话；若已有服务则复用并报告地址。
- 所有命令失败返回非零退出码及统一错误码。

### API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/v1/health` | 健康与版本，不返回环境秘密 |
| GET | `/api/v1/sessions` | 会话摘要列表 |
| POST | `/api/v1/sessions` | 建立基线会话 |
| GET | `/api/v1/sessions/{id}` | 会话详情与合法动作 |
| POST | `/api/v1/sessions/{id}/annotations/import` | 导入批注并生成任务 |
| GET | `/api/v1/sessions/{id}/tasks` | 任务与人工状态 |
| POST | `/api/v1/sessions/{id}/receipt` | 提交并校验 Agent 回执 |
| POST | `/api/v1/sessions/{id}/verify` | 快照结果、Diff、归因和检查 |
| GET | `/api/v1/sessions/{id}/evidence` | 获取任务证据和未声明修改 |
| PUT | `/api/v1/sessions/{id}/tasks/{task_id}/decision` | 保存任务人工决策 |
| PUT | `/api/v1/sessions/{id}/hunks/{hunk_id}/decision` | 保存未声明修改决策 |
| POST | `/api/v1/sessions/{id}/rework` | 生成返工包并推进状态 |
| POST | `/api/v1/sessions/{id}/accept` | 校验门槛并接受会话 |

所有响应有 Pydantic 模型。统一错误：

```json
{
  "error": {
    "code": "STALE_BASELINE",
    "message": "源文件与本会话基线不一致，不能按当前回执验收。",
    "details": {"sessionId": "ses_..."}
  }
}
```

`details` 不得含绝对敏感路径、堆栈或文档原文。状态修改接口必须具备幂等语义；重复提交同一 decision 得到同一结果。

### 性能与异步边界

P0 验证为同步请求，2 MiB 文件在开发机上的目标 P95 小于 3 秒。若技术尖峰未达到，必须改为持久化任务 + 轮询，不得让请求无限等待；本阶段不为进度动画引入 SSE。

## 八、Prompt 设计

本阶段不包含模型 Prompt。`agent-brief.md` 和 `rework-brief.md` 是确定性模板，不是模型 Prompt 源码，但仍需版本控制并包含：

- session ID、base hash、目标文件相对路径；
- 每条 task ID、原意见、锚点上下文、授权范围；
- 只允许修改目标工作区文件的约束；
- `receipt.json` 输出格式、合法 outcome 和正反例；
- 禁止仅口头声称完成、禁止改写已接受任务；
- 无法完成时使用 `clarification` 或 `blocked`，不得猜测。

## 九、验收界面或纵向切片

这是正式产品的第一条 Web 纵向切片，不是一次性调试页。

### 页面

1. `/sessions`：会话列表、源文件名、阶段、任务进度、未声明修改数。
2. `/sessions/[id]`：顶部会话摘要；任务筛选；任务卡；未声明修改区；接受/返工操作。

### 任务卡信息顺序

1. 原始批注和定位状态；
2. 修改前与修改后；
3. 关联 Diff hunk；
4. Agent outcome 与摘要，明确标为“Agent 声明”；
5. 确定性检查和证据，明确标为“机器检查”；
6. 接受、返工、需澄清及原因输入。

### 交互边界

- 不在 P0 内编辑 Markdown 正文；
- 不以颜色作为唯一状态表达；
- 低置信归因和失败检查必须有文字说明；
- 加载、空状态、损坏数据、过期基线、保存失败均有可恢复提示；
- 目标宽度：桌面 1280px；移动端仅保证可读，不承诺完整高效审阅。

## 十、测试要求

- 第一层：后端 pytest、API 集成、前端类型检查/ESLint、前端组件测试、Playwright 关键流程。
- 第二层：本阶段无模型调用，不运行真实模型冒烟；用真实 Plannotator（若成功锁定）完成一条外部工具集成冒烟。
- 恢复：每个可写状态后强制重启服务，再确认可继续。
- 文件安全：路径遍历、工作区外路径、符号链接、非 UTF-8、非 Markdown、超限文件。
- 失败注入和人工样例见 `docs/05-测试与验收方案.md`。

不得删除失败测试、降低断言或将人工未验收写成通过。

## 十一、验收清单

产品经理按以下步骤操作：

- [ ] 运行环境检查，看到 Python、Node、Plannotator、端口和工作区的明确状态。
- [ ] 选择一份 3,000 字以上 Markdown，开始审阅并完成至少 5 条批注。
- [ ] 打开生成的 `agent-brief.md`，确认每条意见和上下文都可识别。
- [ ] 让一个外部 Agent 修改文档并生成回执。
- [ ] 提交回执，确认错误 hash 或缺少字段会被拒绝。
- [ ] 打开验收页，逐条看到原意见、修改前后、Diff、Agent 声明和机器检查。
- [ ] 注入一处无关修改，确认它出现在“未声明修改”中。
- [ ] 对部分任务点击接受、部分点击返工，刷新页面并重启服务，确认选择仍在。
- [ ] 生成返工包，确认只包含未通过项，且明确保护已接受项。
- [ ] 未处理完全部任务时尝试接受会话，确认系统阻止并解释原因。
- [ ] 完成所有决定并接受会话，确认结果成为下一轮基线且历史记录仍可查看。
- [ ] 对三份真实文档重复流程，记录验收耗时和是否仍需全文重读。

## 十二、风险与待确认项

### 已知风险

- Plannotator CLI/JSON 契约可能变化：用独立适配器、版本探测、fixture 和通用导入入口隔离。
- 相同段落导致锚点歧义：多证据定位；不唯一时标记 ambiguous，交给人确认。
- 行级 Diff 对大范围移动可读性差：P0 保留真实 hunk 和低置信提示，P1 再引入 AST 结构 Diff。
- Agent 回执可能伪造：所有声明必须与真实快照和 Diff 交叉验证。
- 本地服务被其他页面调用：仅监听 loopback，并校验 Origin/Host；状态修改接口使用启动时本地会话 token 或等价 CSRF 防护，不把 token 写入 URL/日志。

### 待确认项

无产品决策阻塞项。Plannotator 精确版本由技术尖峰依据实际可安装版本锁定；如果无法可靠调用，第一阶段必须保留通用 JSON 导入闭环并如实标记“外部批注器集成待验”，不得伪造通过，也不得把第 1 阶段标记为完成。

## 十三、交接给下一阶段

第 1 阶段通过后，下一阶段可复用：稳定领域 schema、会话状态机、不可变快照、行级 Diff、任务验收 UI、失败样例和 Agent 回执协议。只有在真实验收暴露明确问题时，才新增 AST Diff、语义验证或锚点迁移。
